## News, About and public participants

Routine News is projected on server reads from published registration windows, dated schedule entries, released mappools, public fixtures and approved published results. Stable event URLs are deterministic; future dates stay labelled as plans, and passing a scheduled date never proves completion. Withdrawn publication and result corrections appear on the next request. Home shares this request-scoped projection, shows at most three updates and the nearest confirmed future milestone. No cron, provider API calls, writes on GET or additional News store is involved. Captain/draft snapshots without a reliable publication timestamp are not assigned invented announcement dates.

Optional approved editorial content lives in `src/content/announcements.json` (or mounted `OCLR_ANNOUNCEMENTS_FILE`). Each entry has a unique slug, title, summary, publication flag/time and plain-text heading/body sections. Set `published: false` while drafting; published entries require a date and future-dated entries stay hidden until that time. Text is escaped, not executed as HTML. Add/review content in Git and redeploy, or atomically replace the approved mounted file; there is no CMS or separate editorial service. Production content starts empty. Synthetic announcements are restricted to tests.

About lists only active persistent staff grants explicitly marked **Show on About** in `/admin/staff`. Visibility defaults off, is audited and scope-authorized, and is separate from permission grants. Unpublished edition assignments and bootstrap environment accounts never become an automatic public roster; revoked roles disappear on the next read. Public fields are limited to username, osu! profile/avatar and published role/scope. About and Privacy use the same explicitly approved `PRIVACY_CONTACT_OSU_ID`; no separate contact identity is configured in source. Do not infer organizer identity from repository ownership. Participant pages show explicitly published captain identities and finalized published team rosters; they never enumerate individual applications or automatically announce accepted/unpicked players. Public pool disclosure remains a separately approved draft-board setting. Privacy/correction/removal requests use the approved privacy contact.

## Public player directory

`/tournaments/[edition]/players` and `/api/tournaments/[edition]/players` list every accepted registration in that published edition. The page displays the complete matching collection without pagination or a load-more control (#245). Username, osu! ID and accepted participation are automatically public, as explained before submission and in Privacy. Application answers, contact fields and staff notes are never queried. Captain/team/roster details retain separate publication checks. Pending/rejected/withdrawn registrations and unpublished editions stay private. Legacy `/players?edition=...` redirects into the edition; `/players` redirects to Tournaments. The legacy directory API requires one edition and cannot return a cross-edition list. `/dashboard` remains private.

Current and historical player pages share search, public-team and role filters, stable sorting, applied-condition chips, result/season counts and reset (#425). Search includes literal names, UIDs, visible name evidence and published team names. Only reliably available season data produces filter options; unknown teams do not become free agents. Current accepted Captain/coach combinations can match several roles while appearing once per UID. Historical names, roles and absent statistics remain historical; current caches never supply invented historical rank, PP or Tier.

Page URL state uses `q`, `team`, `role`, `sort`, `group`, `rankMin`, `rankMax`, `ppMin` and `ppMax`. `sort` accepts `default`, `name-asc`, `name-desc`, `rank-asc`, `rank-desc`, `pp-asc` and `pp-desc`; `group` accepts `list` or `team`. Team values are published team IDs; `free_agent` is available only for explicitly recorded free agents. Ranges include both endpoints, reject invalid/reversed bounds and exclude missing values. Rank uses positive integer placement (smaller is better); PP zero is valid. Both sort directions put missing metrics last and break ties by ascending UID. Group mode sorts inside each original team group. Reset restores the full season, source order and default grouping. Tier filtering is deferred.

The removed `ranked` and `hasPp` presence filters are ignored in old links and cleared on the next filter update. Advanced rank/PP ranges are grouped in a shared collapsible panel.

These extended query parameters belong to the page UI, not new API filters. The page loads the full publication-checked read model once (completing remote collection pages when needed) and changes URL state through native browser history. Filter changes do not reload the page or fetch provider statistics; message boards retain their keyed identity across sorting/group changes. Mobile keeps search and sorting visible and can collapse other controls. Existing directory API contracts and background statistics refresh/revalidation remain in place.

## Dashboard participation history (#361)

The private `/dashboard` shows the signed-in UID's saved participation in published historical archives and completed native tournaments, newest numeric season first (unknown seasons last). It includes history-only players without a native registration, preserves historical names and distinct roles/teams, and keeps registration actions in their existing section. Missing fields remain unrecorded; a failed history read offers a retry instead of an empty-history message.

The list reuses `publicPlayer`, public tournament summaries and their existing remote resources. Archive facts take precedence over duplicate native/imported registrations; multiple confirmed roster/replacement facts in one edition remain separate. Names never match identities. Unpublished editions, unresolved UIDs, application answers and source appendices do not appear. The updated backend supplies all same-edition facts using the existing response shape; an older backend can only supply the facts its saved-read implementation already exposes. No migration or new Developer scope is required.

## osu! player profile snapshots

Published directory and team entries link to `/players/[osuId]`; `?edition=<slug>` preserves tournament context and `mode=osu|taiko|fruits|mania` selects an explicitly labeled ruleset. Directory reads and Next.js link prefetching never fetch provider profiles. Profile pages and `/api/players/[osuId]` check published participation before looking up metadata and again after provider I/O. A cached profile does not make a private applicant public. Anonymous refresh parameters are rejected.

`getOsuUserProfile(id, mode)` reuses the [official user endpoint](https://osu.ppy.sh/docs/#get-user) through the existing application `public` token. The fixed path includes `key=id` to prevent legacy numeric-username fallback; returned IDs are verified. No new player OAuth scopes or retained provider tokens are required. Only a compact validated public projection is stored in `user_profile_cache`, independently of participation and OAuth identity. Optional unavailable/invalid fields become null; unsafe numeric scores are omitted rather than rounded, while exact score strings retain precision. Provider contact fields and account history are discarded. Successful lookup updates only an existing user's mutable username, preserving all stable references.

Snapshots expire after **30 minutes** and are labeled with their source, ruleset and last successful update. The PostgreSQL cache holds at most **1,000 ID/ruleset keys**, evicting oldest attempts. In-process coalescing and database refresh claims deduplicate requests across instances; late claims cannot overwrite newer work. Refresh attempts are spaced by at least one minute per key, with five-minute backoff after failure. Temporary failures retain the last good snapshot with a stale notice; closed/deleted profiles are unavailable while their previous snapshot remains stored. Per-process provider pacing/queue limits still apply; account for aggregate traffic when scaling processes.

Profile lookup is API-only: the protected `POST /api/admin/profiles` supplies in-context Captain identity enrichment and throttled refresh for Admins with registration permissions. There is no standalone Profile or Beatmap lookup page; beatmap previews and bulk lookup stay in the Mappool workflow. Mappoolers, Referees, captains and ordinary accounts have no lookup privilege through those roles. Lookup never creates a user, publishes participation, changes eligibility or approves a registration. Use the organizer regression input `https://osu.ppy.sh/users/651307/osu` after configuring real API credentials. Automated fixtures are synthetic; the unauthenticated official request returned HTTP 403, so that player's current statistics remain unverified.

## Public competition center and group standings

Current and historical tournament rules are read on the selected edition's main page at `/tournaments/{edition}#rules`. The tournament menu has no separate Rules destination, and registration acknowledgements open this same section. Published versions, eligibility, contents, historical illustrations and unavailable-rule states remain on the homepage. The legacy `/rules` route only redirects: JavaScript maps recognized chapter fragments to the corresponding homepage anchor; unknown fragments and browsers without JavaScript fall back to that edition's `#rules`. It has a homepage canonical and is excluded from indexing. Private archive previews and Admin rule editing remain separate from public navigation.

Anonymous visitors can browse edition Players, Mappools, Schedule, Results, Bracket, participant/team pages and `/tournaments/[edition]/matches/[fixtureId]`. Edition navigation exposes these destinations even before publication, with meaningful empty states. The results list filters stage, round and publication status; scheduled fixtures can exist without scores. Public match details show approved team totals, included beatmaps/mods, a released-mappool link, an explicit public note, MP source and publication time. Private imports, player-level provider scores, review reasons, actor IDs and substitutions are never part of public result DTOs.

Public GET `/api/tournaments/[edition]/matches`, `/matches/[fixtureId]` and `/bracket` need no cookies. Their database queries require fixture publication and explicitly approved published revisions; direct private IDs return 404. There is no public result-write endpoint. Dynamic rendering and no-store responses keep publication withdrawal visible immediately; staff mutations also invalidate the edition layout.

Admin configures named groups and official team membership under the fixture workspace, then explicitly publishes those assignments. A team may belong to one group in an edition's Group Stage. Round-specific ranking policies require approved win/loss points, optional confirmed draw points and ordered supported criteria (points, wins, map difference, maps won). No default points, group assignment or alphabetical tiebreak is supplied. Only published group results count; knockout/cancelled fixtures are excluded. Missing or inconsistent ranking rules produce factual statistics with points/ranks pending. Equal final criteria remain tied. Group/rule changes are audited and do not rewrite source scores.

## Global contributor directory

Global Admins manage the About contributor list at `/admin/contributors` independently of staff roles and tournament editions. Add or edit a literal display name and positive numeric osu! ID; profile links and avatars use the existing canonical osu! identity components. Entries need no site account. Move entries up/down to set display order, select **Show on About** explicitly, then save the entire list. New entries are hidden. Removing a row is a draft change until saved.

The server checks global authorization and the saved revision, rejects duplicate identities, and saves the directory and its audit event in one transaction. A conflict keeps the saved list intact and asks the operator to refresh. Developer access is read-only; edition Admin grants do not authorize global edits. The central audit browser includes contributor changes under the site module. Public rendering projects only the published name and osu! ID.

Migration `0043_contributor_directory` initializes the two formerly hardcoded, already-public contributors in their existing order. Repeated migrations/initialization do not duplicate or restore entries deliberately removed later. Apply it before serving this version. It does not create accounts or grant/revoke any role.
